## 3. Commands (scripts that exist today)

- `yarn install` : install dependencies (runs `patch-package`).
- `yarn start` / `yarn start:reset` : Metro, optionally clearing cache.
- `yarn android` / `yarn ios` : run debug builds. `yarn android:release`, `yarn ios:release` : release configuration.
- `yarn lint` : ESLint.
- `yarn type-check` : `tsc --noEmit` (must stay at 0 errors).
- `yarn format <files>` / `yarn format:check <files>` : Prettier on the given files.
- `yarn check:ratchet` : compares ESLint, TypeScript and Prettier counts with `docs/quality-baseline.json`; `--update` lowers the baseline.
- `yarn test` : Jest unit tests.
- `yarn emulators` : starts the Firestore and Storage emulators (needs the Firebase CLI installed globally and JDK 21 or newer).
- `yarn test:rules` : Firestore and Storage rules tests in the local emulator (needs JDK 21 or newer; no live project is touched).
- `yarn functions:build`, `yarn test:functions` : build and unit-test the Cloud Functions in `functions/` (it has its own `package.json` and `yarn.lock`; run `yarn --cwd functions install` once).
- `yarn test:triggers` : builds the functions and runs `functions/test/triggers.emulator.test.mjs` against the Firestore and Functions emulators (needs JDK 21 or newer; demo project, no live project is touched). Never deploy functions without owner approval.
- `yarn test:backfill` : runs `functions/test/backfill.emulator.test.mjs` against the Firestore emulator (same requirements).
- Backfill: `yarn --cwd functions backfill --project <id> [--apply] [--only users,transactions,splits,settlements,ious,savingsHistory] [--limit N] [--report file.json] [--expect-clean]`. Dry run is the default and writes nothing. `--project` is mandatory. Run it against the emulator (with `FIRESTORE_EMULATOR_HOST` set) first. Applying to a real project is refused unless `--apply --confirm-project <same id> --backup-confirmed` are all given, and must only happen after the owner approves it and a fresh Firestore export exists. A real run also needs Admin credentials for that project (none are set up on the development machine). The report lists counts and document paths only.
- `yarn build:android` : release APK. `yarn build:android:bundle` : release AAB. `yarn build:clean` : Gradle clean.
- `yarn version:bump` : `scripts/bump-version.js` (stamps `app.json` `version`, `android.versionCode` and `ios.buildNumber` from `package.json` and the current time).
- `yarn release:android:local` : the way to build the production Android AAB (`scripts/local-release.sh`; see the release note in section 7 and the gotcha "Production builds are local"). It builds on this Mac in about 6 minutes, with the EAS production variables, the upload key from `credentials/android/` and the Sentry upload, then checks the signing key, the ABIs, the update channel and that `NOTIFICATION_SERVER_URL` is not in the bundle. It sets `RELEASE_UPDATE_CHANNEL=production`, which `plugins/with-update-channel.js` writes into the manifest as the EAS Update channel (`eas build` does this itself; a local build without it can never receive an update). The AAB is `android/app/build/outputs/bundle/release/app-release.aab`.
- EAS (CLI installed globally, logged in as the owner; project ID in `app.json`, owner `chhedadhruv`): `eas build --profile preview|production --platform android|ios` and `eas update --channel <channel>`. Profiles and channels are in `eas.json` (development, preview, production). `runtimeVersion` uses the `fingerprint` policy, so an update only reaches binaries with identical native code. The first preview Android build (2026-11-09, build `9641385f-2089-4ef3-a0a8-abd8329f0e87`) succeeded and was checked on the emulator. Updates are published only with `bash scripts/ota-release.sh` (see the gotcha "Publishing an over-the-air update"); the first production updates went out on 2026-11-13 to 1.5.1 and were confirmed on a Play-installed phone. EAS builds need Node 24 (`.nvmrc`, `engines`, the `base` profile in `eas.json`), because `@firebase/ai` requires Node `>=24.12.0`. The Firebase config files must be identical locally and in the EAS file variables `GOOGLE_SERVICES_JSON` and `GOOGLE_SERVICE_INFO_PLIST` (see `docs/deferred-tasks.md`). EAS Doctor runs on every build (it cannot run through the local `yarn expo` CLI): keep `.expo/` ignored and keep one version of each native module. EAS decompression tip: build logs from `eas build:view --json` (`logFiles`) are brotli-compressed. Never run `eas update` or `eas build` without owner approval.
- Revopush (CodePush) is gone: the package and its release scripts were removed in the Expo conversion, and its deployment keys were removed from `env.example` and the local `.env` on 2026-11-13. Over-the-air updates are EAS Update only. Builds before 1.4.0 still contain CodePush and still ask Revopush for updates; nothing is published there any more.
- Never use `npx`: run Expo through yarn (`yarn expo prebuild --clean`, `yarn expo install <pkg>`, `yarn expo install --check`). `android/` and `ios/` are gitignored and rebuilt by `yarn expo prebuild --clean --no-install` (`yarn android` and `yarn ios` run it when the folders are missing). Signing files and Firebase config are not committed; a fresh checkout needs these local files first: `credentials/android/keystore.properties` and `credentials/android/<keystore file>` (copied into `android/` by `plugins/with-release-signing.js`), `google-services.json` and `GoogleService-Info.plist` at the repo root (copied in by the Firebase plugin), and `.env`.
- iOS after dependency changes: `cd ios && pod install`.
- iOS simulator build when `yarn ios` fails (no `Simulator.app`): `xcodebuild` with `-destination id=<simulator>`, then `xcrun simctl install` and `launch`; the app target needs an iOS 26 simulator.

- `bash scripts/ota-release.sh <preview|production> "<message>" [--runtime <hash>] [--confirm-production]` : publishes an over-the-air update for Android (see the gotcha "Publishing an over-the-air update"). It has no `yarn` script on purpose: `package.json` scripts are part of the fingerprint.

## 5. Hard rules

- Yarn only; never npm or npx; never create `package-lock.json`.
- No AI attributions of any kind in commit messages, pull request descriptions, code comments, or docs.
- No emojis anywhere (UI, copy, comments, notifications). Icons are SVG only: `lucide-react-native` for UI icons, custom `react-native-svg` components for category icons and illustrations.
- Never hardcode secrets; keys come from environment variables or EAS secrets. Never print or commit credential files.
- Never change the package name, bundle ID, or signing credentials.
- TypeScript strict on new and touched files; no `any`.

## 7. Git and release workflow

- Branches: `main` (legacy default), `develop`, `staging`, `production` (created in Phase 1a). As of 2026-11-10 `develop` is 82 commits behind `main` and unused: every PR since Phase 1 was cut from `main` and merged into `main`, so cut feature branches from `main` until the owner decides whether to retire `develop` or bring it up to date.
- Conventional Commits: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.
- Push to `staging` or `production`: if `version` or `runtimeVersion` changed, run an EAS build; otherwise publish an EAS Update to the matching channel. Production also runs EAS Submit to both stores. (Needs the Expo conversion in Phase 1b.)
- Never push directly to `production`.
- Today: change `package.json` `version`, then run `yarn version:bump` (it stamps `app.json` `version`, `android.versionCode` and `ios.buildNumber`); Play rejects a versionCode it has already seen, so a rebuild needs a new bump. JavaScript-only changes reach 1.5.1 over the air: merge to `main`, check that the fingerprint is still the store build's runtime version, then `bash scripts/ota-release.sh production "<message>" --runtime <hash> --confirm-production` with the owner's approval. A change that moves the fingerprint (a native module, `app.json`, `plugins/`, `package.json` scripts or dependencies) needs a new store build.
- Android store build, in order: version bump merged to `main`, then `yarn release:android:local` from a clean `main` (this replaces `eas build --profile production`, which runs out of memory on the free plan), then the owner uploads `app-release.aab` in Play Console to Internal testing, installs it on a phone and runs the checklist (Google sign-in, a push tap, camera and gallery photos, add/edit/delete expense, settle-up, the date pickers, both themes), then promotes it to production at the percentage the owner chooses (a staged rollout, about 20 percent held for 48 hours is the recommendation). The Play listing icon and feature graphic are in `../trackaexpense-audit/store-listing/final/`. Never upload to the production track or choose a percentage without the owner's approval.

## 8. Live-app safety

- Money today: JS floats in major units; `amount` is `string | number` and is a string on 97 percent of live transactions (`src/types/index.ts`). Target: integer minor units. Migration status: not started.
- Data migrations are additive: new field, backfill, app reads both, verify, remove old field in a later release. Take a Firestore export backup first.
- Firestore and Storage rules roll out in stages and are never deployed without owner approval. Stage 1 rules and indexes are deployed from `firebase/`; run `yarn test:rules` before any change. The old open rules in `firebase/baseline/` are for rollback only.
- OTA updates must never rely on native code missing from the live binary; bump `runtimeVersion` on native changes.
- Store rollouts are staged.

After the store release, remove the stale Crashlytics and Analytics data streams in the Firebase console if wanted.

## 12. Known gotchas

- Phase 2 money rules (plan in `../trackaexpense-audit/08-phase-2-plan.md`, data profile in `09-phase-2-data-profile.md`): new money fields are additive integers in minor units (`amountMinor`, `balanceMinor`, `savingsGoalsMinor` keyed by goal id) with a `currency`; the legacy `amount` and `balance` stay and are never removed in this phase. Old installed apps only write the legacy fields, so the triggers in `functions/` derive the new ones; new code reads the minor field with a fallback to the legacy one. Round half away from zero at the currency's minor unit; values that cannot be converted are skipped and reported, never fatal. Do not rewrite the `savingsGoals` array from a function (an old client may be writing it): the goal minor amounts live in a separate map.
- Splits divide money in integer minor units through `src/utils/splitMath.ts` (`sharesMinor`, `shareOfMinor`): the shares of a split always add up to its total, and where it does not divide evenly the first participants get the extra minor unit. Do not reintroduce `amount / splitUsers.length` or `amount * percentage / 100` in a screen. Group and friend balances are summed as integers; the payer's own split transaction and its balance change use the same rounded amount, and deleting a split now restores the payer's balance (it used to leave it lower).
- Settle-up rounds the typed amount once to the currency's minor unit and uses that single value for the settlement document, the settlement entry in the splits list, the user's own transaction and both parties' balance increments (the cross-user balance increment of the other member is allowed by the stage 1 rules and still happens from the client). The direction of a balance reversal always follows the removed transaction's own type (expense gives back, income takes away).
- Savings goal arithmetic goes through `addMajor`, `subtractMajor` and `sumValuesMajor` (exact; 0.1 + 0.2 is stored as 0.3). The goals array itself is still rewritten whole by the client and stores only the legacy numbers; the goal minor amounts are derived by the trigger into `savingsGoalsMinor`. Savings history entries gain `amountMinor`, `previousAmountMinor`, `newAmountMinor` and `currency`. Savings never change the user's `balance`. IOU documents gain `amountMinor` and the creator's `currency`.
- App-side money (`src/utils/amounts.ts`; all of it is now done on the app side: transactions, splits, settlements, IOUs and savings; the operational steps are done: the functions are deployed and the backfill was applied on 2026-11-10): read amounts through `minorOf`, `majorOf` and `totalMajor` (they prefer `amountMinor` and fall back to the legacy `amount`; unconvertible values show as before and are left out of totals). Writes keep the legacy `amount` exactly as before (string on add, number on edit) and add `amountMinor` and `currency`. Never `increment` a `balanceMinor` field from the client: for a user without that field it would start from zero and store a wrong total, so only the legacy `balance` is incremented and the trigger derives `balanceMinor`. Every balance change is taken from the rounded minor amount (`balanceEffect`, `editBalanceDelta`), so add, edit and delete of the same transaction cancel exactly.
- Phase 2b: `groups/{id}.memberIds` (array of uids) is derived by the `memberIdsFromGroup` trigger and the backfill (`--only groups`) from the email list `members`, which old apps keep writing and which stays the source of truth. An email with no matching account is left out of `memberIds` and reported as skipped under `members` (6 of 22 groups in the 2026-11-09 export). The app does not read `memberIds` yet: its group queries stay `members array-contains email` until rules stage 2 (2d), which will switch them.
- Phase 2c, user lookup: screens find other users only through `src/services/UserLookup.ts`, which calls the `lookupUsersByContact` callable (`functions/src/lookup.ts`, signed-in callers only, at most 30 lookups per call) and gets back uid, email, name and avatar, nothing else. Never read another user's `users` document from a screen; only the signed-in user's own document may be read directly. There is no fallback to a direct read: if the callable is not deployed or the device is offline the lookup fails and the screen shows its error. The new app therefore needs the functions deployed before it ships. `@react-native-firebase/functions` (27.1.0) is a native module, so it changes the fingerprint. `yarn test:triggers` also starts the Auth emulator for the callable test.
- Phase 2c, settle-up: settlements are recorded and deleted only by the `recordSettlement` and `deleteSettlement` callables (`functions/src/settlement.ts`, client wrapper `src/services/SettlementService.ts`), each in one Firestore transaction. Record writes the settlement, the splits-list entry (id = request id, `settlementId` set), the legacy `balance` of both people (`increment`; the trigger derives `balanceMinor`) and a "Settlement" transaction for each person (the caller's only if they chose to include it; the other person's always, which the undeployed notification server was meant to do). The caller must be one of the two people or the group creator. The screen keeps one request id across a failed attempt, so a retry cannot apply it twice. Delete reverses both balances and removes the split entry, the linked settlement (by id, or for older settlements the single one with the same people, amount and time) and both people's transactions; deleting twice is harmless. Screens must not write `settlements`, settlement-type splits or another user's balance. History entries and notifications stay on the client. `yarn test:settlement` runs the emulator tests.
- Phase 2c, invitations: accepting or declining a group invitation goes only through the `respondToInvitation` callable (`functions/src/invitation.ts`, client wrapper `src/services/InvitationService.ts`).
