# TrackaExpense project guidance

Guidance for working in this repository.

## 1. Project

- TrackaExpense is a personal finance app: expenses, income, statistics, group splits, IOUs, savings goals, budgets, recurring transactions and credit cards.
- Platforms: Android and iOS, both shipped (iOS 1.6.0 is live on the App Store).
- Backend: one Firebase project, with Cloud Functions in `asia-south1`.

## 2. Stack

| Area      | Choice                                                                                   |
| --------- | ---------------------------------------------------------------------------------------- |
| Runtime   | Expo SDK 58, React Native 0.88, React 19, Hermes, New Architecture                        |
| Language  | TypeScript strict (a few legacy JS files remain)                                         |
| Routing   | Expo Router (`app/`)                                                                     |
| Styling   | NativeWind v4 with a semantic theme (light, dark, system)                                |
| State     | TanStack Query v5 persisted to MMKV, Zustand                                             |
| Firebase  | RN Firebase v27: auth, firestore, storage, functions, messaging, perf, remote-config     |
| Errors    | Sentry                                                                                   |
| Analytics | Mixpanel                                                                                 |
| Push      | OneSignal, sent from Cloud Functions only                                                |
| Charts    | Victory Native XL on Skia                                                                |
| OTA       | EAS Update (runtime version from the Expo fingerprint policy)                            |

## 3. Commands

- `yarn install`, `yarn start`, `yarn android`, `yarn ios`.
- `yarn lint`, `yarn type-check` (must stay at 0 errors), `yarn format`, `yarn check:ratchet`.
- `yarn test` (Jest), `yarn test:rules` (Firestore and Storage rules in the emulator, needs JDK 21 or newer).
- `yarn functions:build`, `yarn test:functions`, `yarn test:triggers`, `yarn test:backfill` for the Cloud Functions in `functions/` (its own `package.json`; run `yarn --cwd functions install` once).
- Backfill script: dry run is the default and writes nothing. Applying to a real project needs explicit confirmation flags and a fresh backup.
- Never use `npx`: run Expo through yarn. `android/` and `ios/` are generated by `yarn expo prebuild --clean` and are gitignored.
- A fresh checkout needs local, untracked files: `.env` (see `env.example`), the Firebase config files from your own Firebase project, and signing files for release builds.

## 4. Folder map

- `app/` : Expo Router routes. Route files only re-export or wrap a screen.
- `screens/` : screens (`SplitScreens/` for groups, splits, IOUs, invitations).
- `src/` : shared code: `components/`, `theme/`, `data/`, `hooks/`, `services/`, `utils/`, `types/`.
- `components/`, `utils/`, `services/`, `navigation/` : older shared code.
- `functions/` : Cloud Functions (TypeScript). `src/derive.ts` and `src/sources.ts` hold the money derivations shared by triggers and the backfill.
- `firebase/` : Firestore and Storage rules, indexes and rules tests.
- `plugins/` : local Expo config plugins. `config/` : files injected into the native build. `scripts/` : release helpers.
- `.maestro/` : end-to-end flows.

## 5. Hard rules

- Yarn only; never npm or npx.
- No emojis anywhere. Icons are SVG only (`lucide-react-native`, imported one by one, or small `react-native-svg` components).
- Never hardcode or commit secrets; keys come from environment variables or secret stores.
- TypeScript strict on new and touched files; no `any`.
- Never change the package name, bundle ID or signing credentials.

## 6. Quality gates

- Pre-commit: ESLint, TypeScript, Prettier and related Jest tests (`.husky/pre-commit`). Commit messages follow Conventional Commits. Pre-push runs the full tests and the ratchet.
- The ratchet (`docs/quality-baseline.json`) only allows counts to go down.
- Never commit while a gate is failing and never use `--no-verify`.

## 7. Money and data rules

- Money is stored in integer minor units (`amountMinor`, `balanceMinor`) next to the legacy `amount` and `balance`, which old app versions still write. Cloud Function triggers derive the new fields. Read through `minorOf`, `majorOf` and `totalMajor` in `src/utils/amounts.ts`.
- Never `increment` a `balanceMinor` field from the client. Only the legacy `balance` is incremented.
- Splits divide in integer minor units through `src/utils/splitMath.ts` so shares always add up to the total.
- Settlements are recorded and deleted only by callable functions, each in one Firestore transaction.
- Other users are looked up only through the `lookupUsersByContact` callable. Never read another user's profile document from a screen.
- Push notifications are sent only from Cloud Functions.
- Data migrations are additive: add the field, backfill, read both, verify, and remove the old field in a later release.
- Firestore and Storage rules roll out in stages. Run `yarn test:rules` before any change.

## 8. App architecture notes

- The signed-in user's profile and transactions live in one TanStack Query cache. `DataSync` keeps live Firestore listeners that write into the cache. Screens only observe it. The cache is saved to MMKV and wiped on sign-out.
- A screen that writes from what it shows must wait for the listener's `live` confirmation.
- Offline: Firestore's own persistence queues writes on the phone, and `src/services/ConnectivityService.ts` (NetInfo, rules in `src/utils/connectivity.ts`) tracks whether the phone is online and drives the banner (`OfflineBanner`). Add Expense, Add Income, Edit and Delete write with an atomic `writeBatch`, not `runTransaction` (a transaction cannot run offline), and wait through `settleWrite` (`src/utils/offlineWrite.ts`): online it awaits the server so errors reach the screen, offline it returns at once with `queued: true` and a later failure goes to `reportError`. Edit works out the balance change from the transaction it was opened with, not from a fresh server read. Still online-only because they are callables, server transactions or uploads: settlements, undoing a card bill payment, receipt photo upload and removal. New write paths that must work offline follow the same pattern; the airplane-mode flow is `.maestro/flows/offline-expense.yaml`.
- Theme tokens live in `src/theme/palettes.ts`. New screens must use the tokens (NativeWind classes such as `bg-surface`) and be checked in both themes.
- Use the shared `KeyboardAwareScrollView` and `KeyboardAvoidingModal` for any input. Report results with the snackbar store; use `Alert.alert` only for confirmations.
- Dates use the native date picker through `DatePickerModal`.
- Transaction tags, receipt photos, credit cards and budgets each have a small pure-function module in `src/utils/` that holds their rules. Add logic there first, with a test.
- Category guesses go through `src/utils/categorySuggest.ts`: the person's own history first (from the transactions cache, without entries the app wrote itself), then the keyword maps in `utils/CategoryData.ts` matched on whole words. `useCategorySuggestion` keeps the category following the title until the person picks one by hand. Keyword map values must be categories of their list (tested). Title autocomplete (`src/utils/titleSuggest.ts`, `useTitleSuggestions`, `TitleSuggestions`) offers past titles from the same history while the title field is focused; picking one also offers its last category through `applyGuess`, which never overrides a hand pick. Create Split learns from the group's own splits (settlements left out).
- Custom categories: `users/{uid}/categories/{id}` (`name`, `type`, `icon` key from `src/constants/categoryIcons.ts`, never rename or remove a key) and `users/{uid}/categories/_prefs` (hidden built-in values and the order per type); owner-only, no rules change. A transaction still stores the category as plain text, so old apps, Statistics and the server treat a custom one like any unknown category. Read lists through `useCategoryLists(type)` and icons through `useCategoryIcon()` (`src/data/categories.ts`), never the fixed lists, in personal forms. Group splits keep `SPLIT_CATEGORIES`. Savings goals are a third type (`goal`, built-in list `GOAL_CATEGORIES` with lowercase ids that must never change, "other" is the empty value); a goal rename moves the goals through `saveGoals`, never by writing the array directly. Renaming moves the person's own transactions, recurring rules and budgets in batches (`CategoryService.renameCategory`, only the `category` field) and keeps `renamingFrom` until it finishes, so an interrupted rename can be finished later. Deleting leaves past entries with the name.
- Server logic that mirrors app logic (budgets, recurring dates, goals, card periods) exists in both `src/utils/` and `functions/src/`. Change both together.

## 9. Releases

- Native changes (any Expo module, plugin or `app.json` change) change the Expo fingerprint and need a new store build. JavaScript-only changes can ship over the air to binaries with the same runtime version.
- Never work around a fingerprint mismatch: it means the change needs a store build.
- Do not add or change `package.json` scripts if the change is meant to ship over the air, because scripts are part of the fingerprint.
- Run `yarn version:bump` before every store build.
- Store rollouts are staged.

## 10. Third-party services

- Sentry: user context is the uid only. Report handled errors through `reportError()` in `src/services/ErrorReporter.ts`. It does not start in development builds.
- Mixpanel: add events only through `AnalyticsService`, with no names, titles, exact amounts or ids on them. The catalogue and rules are in `docs/analytics.md`; the Profile "Usage analytics" switch must keep working (`MixpanelService.setAnalyticsEnabled`).
- OneSignal: identity is the Firebase uid. The REST key is a Cloud Functions secret, never in a file.
- Keys live in the gitignored `.env`; names are in `env.example`.

## 11. Known gotchas

- Pin `**/firebase` in `resolutions` so a single copy of the Firestore JS SDK is installed, or the rules tests fail.
- RN Firebase v27: `snapshot.exists()` is a method.
- `react-native-mmkv` falls back to an in-memory mock when `JEST_WORKER_ID` is set; `metro.config.js` shims that check. After any Metro, Expo or MMKV upgrade, confirm the cache really persists on a build.
- Do not add `expo-notifications`: it registers a second Android messaging service that competes with RN Firebase and OneSignal.
- Do not add `firebase-tools` to the app's dependencies; install the CLI globally.
- After adding a native dependency, run a release build once: R8 shrinking can fail on missing classes that debug builds never show.
- Android permissions are kept minimal and some are blocked in `app.json`. Do not add media permissions; receipt photos use the system picker.
- Lists that can grow are a `FlatList`.
