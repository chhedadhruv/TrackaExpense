## 3. Commands (scripts that exist today)

- `yarn install` : install dependencies (runs `patch-package`).
- `yarn start` / `yarn start:reset` : Metro, optionally clearing cache.
- `yarn android` / `yarn ios` : run debug builds. `yarn android:release`, `yarn ios:release` : release configuration.
- `yarn lint` : ESLint.
- `yarn type-check` : `tsc --noEmit` (must stay at 0 errors).
- `yarn format <files>` / `yarn format:check <files>` : Prettier on the given files.
- `yarn check:ratchet` : compares ESLint, TypeScript and Prettier counts with `docs/quality-baseline.json`; `--update` lowers the baseline.
- `yarn test` : Jest unit tests.
- `yarn emulators` : starts the Firestore and Storage emulators (needs the Firebase CLI installed globally and JDK 21 or newer).
- `yarn test:rules` : Firestore and Storage rules tests in the local emulator (needs JDK 21 or newer; no live project is touched).
- `yarn functions:build`, `yarn test:functions` : build and unit-test the Cloud Functions in `functions/` (it has its own `package.json` and `yarn.lock`; run `yarn --cwd functions install` once).
- `yarn test:triggers` : builds the functions and runs `functions/test/triggers.emulator.test.mjs` against the Firestore and Functions emulators (needs JDK 21 or newer; demo project, no live project is touched). Never deploy functions without owner approval.
- `yarn test:backfill` : runs `functions/test/backfill.emulator.test.mjs` against the Firestore emulator (same requirements).
- Backfill: `yarn --cwd functions backfill --project <id> [--apply] [--only users,transactions,splits,settlements,ious,savingsHistory] [--limit N] [--report file.json] [--expect-clean]`. Dry run is the default and writes nothing. `--project` is mandatory. Run it against the emulator (with `FIRESTORE_EMULATOR_HOST` set) first. Applying to a real project is refused unless `--apply --confirm-project <same id> --backup-confirmed` are all given, and must only happen after the owner approves it and a fresh Firestore export exists. A real run also needs Admin credentials for that project (none are set up on the development machine). The report lists counts and document paths only.
- `yarn build:android` : release APK. `yarn build:android:bundle` : release AAB. `yarn build:clean` : Gradle clean.
- `yarn version:bump` : `scripts/bump-version.js` (stamps `app.json` `version`, `android.versionCode` and `ios.buildNumber` from `package.json` and the current time).
- EAS (CLI installed globally, logged in as the owner; project ID in `app.json`, owner `chhedadhruv`): `eas build --profile preview|production --platform android|ios` and `eas update --channel <channel>`. Profiles and channels are in `eas.json` (development, preview, production). `runtimeVersion` uses the `fingerprint` policy, so an update only reaches binaries with identical native code. The first preview Android build (2026-11-09, build `9641385f-2089-4ef3-a0a8-abd8329f0e87`) succeeded and was checked on the emulator; nothing has been published with `eas update`. EAS builds need Node 24 (`.nvmrc`, `engines`, the `base` profile in `eas.json`), because `@firebase/ai` requires Node `>=24.12.0`. The Firebase config files must be identical locally and in the EAS file variables `GOOGLE_SERVICES_JSON` and `GOOGLE_SERVICE_INFO_PLIST` (see `docs/deferred-tasks.md`). EAS Doctor runs on every build (it cannot run through the local `yarn expo` CLI): keep `.expo/` ignored and keep one version of each native module. EAS decompression tip: build logs from `eas build:view --json` (`logFiles`) are brotli-compressed. Never run `eas update` or `eas build` without owner approval.
- There are no Revopush release scripts (removed with CodePush).
- Never use `npx`: run Expo through yarn (`yarn expo prebuild --clean`, `yarn expo install <pkg>`, `yarn expo install --check`). `android/` and `ios/` are gitignored and rebuilt by `yarn expo prebuild --clean --no-install` (`yarn android` and `yarn ios` run it when the folders are missing). Signing files and Firebase config are not committed; a fresh checkout needs these local files first: `credentials/android/keystore.properties` and `credentials/android/<keystore file>` (copied into `android/` by `plugins/with-release-signing.js`), `google-services.json` and `GoogleService-Info.plist` at the repo root (copied in by the Firebase plugin), and `.env`.
- iOS after dependency changes: `cd ios && pod install`.
- iOS simulator build when `yarn ios` fails (no `Simulator.app`): `xcodebuild` with `-destination id=<simulator>`, then `xcrun simctl install` and `launch`; the app target needs an iOS 26 simulator.

Planned commands: EAS build and update scripts (Phase 1b).

## 5. Hard rules

- Yarn only; never npm or npx; never create `package-lock.json`.
- No AI attributions of any kind in commit messages, pull request descriptions, code comments, or docs.
- No emojis anywhere (UI, copy, comments, notifications). Icons are SVG only: `lucide-react-native` for UI icons, custom `react-native-svg` components for category icons and illustrations.
- Never hardcode secrets; keys come from environment variables or EAS secrets. Never print or commit credential files.
- Never change the package name, bundle ID, or signing credentials.
- TypeScript strict on new and touched files; no `any`.

- Branches: `main` (legacy default), `develop`, `staging`, `production` (created in Phase 1a). As of 2026-11-10 `develop` is 82 commits behind `main` and unused: every PR since Phase 1 was cut from `main` and merged into `main`, so cut feature branches from `main` until the owner decides whether to retire `develop` or bring it up to date.
- Conventional Commits: feat, fix, docs, style, refactor, perf, test, build, ci, chore, revert.
- Push to `staging` or `production`: if `version` or `runtimeVersion` changed, run an EAS build; otherwise publish an EAS Update to the matching channel. Production also runs EAS Submit to both stores. (Needs the Expo conversion in Phase 1b.)

- Today: change `package.json` `version`, then run `yarn version:bump` (it stamps `app.json` `version`, `android.versionCode` and `ios.buildNumber`); Play rejects a versionCode it has already seen, so a rebuild needs a new bump. EAS Update is configured but nothing has been published.

## 8. Live-app safety

- Money today: JS floats in major units; `amount` is `string | number` and is a string on 97 percent of live transactions (`src/types/index.ts`). Target: integer minor units. Migration status: not started.
- Data migrations are additive: new field, backfill, app reads both, verify, remove old field in a later release. Take a Firestore export backup first.
- Firestore and Storage rules roll out in stages and are never deployed without owner approval. Stage 1 rules and indexes are deployed from `firebase/`; run `yarn test:rules` before any change. The old open rules in `firebase/baseline/` are for rollback only.
- OTA updates must never rely on native code missing from the live binary; bump `runtimeVersion` on native changes.
- Store rollouts are staged.

Source map and R8 mapping upload run in EAS release builds (they need `SENTRY_AUTH_TOKEN`). R8 obfuscation is on (PR 52 is merged); the phone test of an obfuscated release build and a readable native trace in Sentry are still to be confirmed (see `docs/deferred-tasks.md`). - OneSignal (live in code, `src/services/PushService.ts`): identity is the Firebase uid (login/logout in `navigation/Routes.tsx`); the permission prompt is deferred until after the first saved expense. Push credentials (Firebase service account for Android, APNs key for iOS) must be added in the OneSignal dashboard before any push is delivered. All sends must come from Cloud Functions, never the client.
- Crashlytics and Firebase Analytics were removed (the `@react-native-firebase/crashlytics` and `@react-native-firebase/analytics` packages, the Crashlytics config plugin and Gradle pin): errors go to Sentry only, product events to Mixpanel only. Screen views are no longer recorded anywhere (they were Firebase Analytics only); add a Mixpanel event through `AnalyticsService` if they are wanted. Still running: Perf and FCM. This is a native change (fingerprint `c3124dc6...` for Android), so it ships only with a store build, never over the air. After the store release, remove the stale Crashlytics and Analytics data streams in the Firebase console if wanted.
- Keys (`SENTRY_DSN`, `MIXPANEL_TOKEN`, `ONESIGNAL_APP_ID`) live in the gitignored `.env`; names are in `.env.example`. Empty values disable the service.

## 12. Known gotchas

- Phase 2 money rules (plan in `../trackaexpense-audit/08-phase-2-plan.md`, data profile in `09-phase-2-data-profile.md`): new money fields are additive integers in minor units (`amountMinor`, `balanceMinor`, `savingsGoalsMinor` keyed by goal id) with a `currency`; the legacy `amount` and `balance` stay and are never removed in this phase. Old installed apps only write the legacy fields, so the triggers in `functions/` derive the new ones; new code reads the minor field with a fallback to the legacy one. Round half away from zero at the currency's minor unit; values that cannot be converted are skipped and reported, never fatal. Do not rewrite the `savingsGoals` array from a function (an old client may be writing it): the goal minor amounts live in a separate map.
- Splits divide money in integer minor units through `src/utils/splitMath.ts` (`sharesMinor`, `shareOfMinor`): the shares of a split always add up to its total, and where it does not divide evenly the first participants get the extra minor unit. Do not reintroduce `amount / splitUsers.length` or `amount * percentage / 100` in a screen. Group and friend balances are summed as integers; the payer's own split transaction and its balance change use the same rounded amount, and deleting a split now restores the payer's balance (it used to leave it lower).
- Settle-up rounds the typed amount once to the currency's minor unit and uses that single value for the settlement document, the settlement entry in the splits list, the user's own transaction and both parties' balance increments (the cross-user balance increment of the other member is allowed by the stage 1 rules and still happens from the client). The direction of a balance reversal always follows the removed transaction's own type (expense gives back, income takes away).
- Savings goal arithmetic goes through `addMajor`, `subtractMajor` and `sumValuesMajor` (exact; 0.1 + 0.2 is stored as 0.3). The goals array itself is still rewritten whole by the client and stores only the legacy numbers; the goal minor amounts are derived by the trigger into `savingsGoalsMinor`. Savings history entries gain `amountMinor`, `previousAmountMinor`, `newAmountMinor` and `currency`. Savings never change the user's `balance`. IOU documents gain `amountMinor` and the creator's `currency`.
- App-side money (`src/utils/amounts.ts`; all of it is now done on the app side: transactions, splits, settlements, IOUs and savings; the operational steps are done: the functions are deployed and the backfill was applied on 2026-11-10): read amounts through `minorOf`, `majorOf` and `totalMajor` (they prefer `amountMinor` and fall back to the legacy `amount`; unconvertible values show as before and are left out of totals). Writes keep the legacy `amount` exactly as before (string on add, number on edit) and add `amountMinor` and `currency`. Never `increment` a `balanceMinor` field from the client: for a user without that field it would start from zero and store a wrong total, so only the legacy `balance` is incremented and the trigger derives `balanceMinor`. Every balance change is taken from the rounded minor amount (`balanceEffect`, `editBalanceDelta`), so add, edit and delete of the same transaction cancel exactly.
- Phase 2b: `groups/{id}.memberIds` (array of uids) is derived by the `memberIdsFromGroup` trigger and the backfill (`--only groups`) from the email list `members`, which old apps keep writing and which stays the source of truth. An email with no matching account is left out of `memberIds` and reported as skipped under `members` (6 of 22 groups in the 2026-11-09 export). The app does not read `memberIds` yet: its group queries stay `members array-contains email` until rules stage 2 (2d), which will switch them.
- Phase 2c, user lookup: screens find other users only through `src/services/UserLookup.ts`, which calls the `lookupUsersByContact` callable (`functions/src/lookup.ts`, signed-in callers only, at most 30 lookups per call) and gets back uid, email, name and avatar, nothing else. Never read another user's `users` document from a screen; only the signed-in user's own document may be read directly. There is no fallback to a direct read: if the callable is not deployed or the device is offline the lookup fails and the screen shows its error. The new app therefore needs the functions deployed before it ships. `@react-native-firebase/functions` (27.1.0) is a native module, so it changes the fingerprint. `yarn test:triggers` also starts the Auth emulator for the callable test.
- Phase 2c, settle-up: settlements are recorded and deleted only by the `recordSettlement` and `deleteSettlement` callables (`functions/src/settlement.ts`, client wrapper `src/services/SettlementService.ts`), each in one Firestore transaction. Record writes the settlement, the splits-list entry (id = request id, `settlementId` set), the legacy `balance` of both people (`increment`; the trigger derives `balanceMinor`) and a "Settlement" transaction for each person (the caller's only if they chose to include it; the other person's always, which the undeployed notification server was meant to do). The caller must be one of the two people or the group creator. The screen keeps one request id across a failed attempt, so a retry cannot apply it twice. Delete reverses both balances and removes the split entry, the linked settlement (by id, or for older settlements the single one with the same people, amount and time) and both people's transactions; deleting twice is harmless. Screens must not write `settlements`, settlement-type splits or another user's balance. History entries and notifications stay on the client. `yarn test:settlement` runs the emulator tests.
- Phase 2c, invitations: accepting or declining a group invitation goes only through the `respondToInvitation` callable (`functions/src/invitation.ts`, client wrapper `src/services/InvitationService.ts`). It identifies the caller by the email in the verified sign-in token (never the profile `email` field, which its owner can edit) and requires `email_verified`; in one transaction it updates the group (`members`, `memberNames`, `pendingInvites`) and the invitation, is harmless when repeated, and refuses to accept for a deleted group. Creating a group, sending and resending invitations stay client writes by the inviter, who is a member. `yarn test:invitation` runs the emulator tests.
- Phase 2c, push sending: the app sends push only through the `sendPush` callable (`functions/src/push.ts`, client wrapper `src/services/PushSender.ts`, called from `services/NotificationService.sendNotificationToUsers`). It may notify the caller, or the members and pending invitees of one group the caller is a member of (request `groupId`); anyone else is dropped. It requires a verified email, caps 50 recipients, 2 KB of data and 200 calls per caller per hour (`pushLimits/{uid}`), sends through the OneSignal REST API by Firebase uid (`include_aliases.external_id`, devices are linked with `OneSignal.login`), and when OneSignal fails or the key is missing stores the in-app copy at `users/{email_at_domain}/notifications`. The app no longer reads other users' `fcmToken` and does not call the Express server. The REST key is the Firebase secret `ONESIGNAL_API_KEY` (never in a file or `.env`): `firebase functions:secrets:set ONESIGNAL_API_KEY --project trackaexpense` must be done by the owner before the functions are deployed. The OneSignal app id is the `ONESIGNAL_APP_ID` param (default set in `index.ts`). `yarn test:push` runs the emulator tests with a fake OneSignal. The Express server in `server/` and the client's own `fcmToken` write are now unused for sending.
- Notification small icon: Android shows the white-on-transparent drawable `ic_stat_onesignal_default` next to a push; without it OneSignal shows a bell. `plugins/with-notification-icon.js` copies `assets/notification-icon/<density>/ic_stat_onesignal_default.png` (the coin stack and arrow of the app icon, no wordmark) into the generated `android/` on every prebuild. To change the icon replace those five PNGs (24, 36, 48, 72 and 96 px, white on transparent); it is a native resource, so it ships only with a store build, not over the air.
- App icon and splash (all native, store build only): `assets/icon.png` is the full-bleed 1024 px icon with no alpha (iOS rejects alpha). Android adaptive icon is `assets/icon-foreground.png` (transparent mark) over `assets/icon-background.png`; keep every part of the mark inside the central 66 percent circle or a launcher mask cuts it. The splash uses its own smaller `assets/splash-icon.png`, not the adaptive foreground: Android 12 and later masks the splash icon to a circle smaller than the adaptive safe zone, and the first attempt clipped the arrow head. Check the splash and the app drawer icon on a real build after any change. The notification icons are a separate set (see above).
- Keyboard and inputs: use `src/components/KeyboardAwareScrollView.tsx` (not the library's own) for any screen with inputs, and `src/components/KeyboardAvoidingModal.tsx` for every React Native `Modal` that contains an input. A modal is its own window, so the screen's keyboard handling does not reach it, and the library default offset of 0 leaves the focused field flush against the keyboard.
- Snackbar: report results and errors with `snackbar.success/error/info(...)` from `src/utils/snackbarStore.ts` (a singleton that works in screens and services; the host `SnackbarHost` is mounted once in `App.tsx`, `src/components/Snackbar.tsx`). `Alert.alert` is only for confirmations (delete, sign out, discard) and prompts that need a choice. A React Native `Modal` is its own window and hides the root host, so every `Modal` renders `<ModalSnackbar />` as its last child (`KeyboardAvoidingModal` already does); react-native-paper `Portal` modals draw in the main window and need nothing. Import lucide icons one by one (`lucide-react-native/icons/circle-check`): the package barrel pulls about 4,700 modules into Metro.
- Theme (`src/theme`): semantic colour tokens in `palettes.ts` (light equals the old constants in `src/constants/theme.ts`; dark is neutral charcoal), `ThemeProvider` (mounted in `App.tsx`; persists the System, Light or Dark choice in AsyncStorage under `theme.mode` and calls `Appearance.setColorScheme` so native dialogs follow) and `useTheme()`. For a StyleSheet screen write `const createStyles = (colors: ThemeColors) => StyleSheet.create({...})` at module level and `const styles = useThemedStyles(createStyles)` in the component; use `colors.primaryFill` with `colors.onPrimary` text for button fills and `colors.primary` for text, icons and borders. Converted so far: the shell (status bar, navigation and tab bar, Paper theme, error and force-update screens, snackbar), Home and Profile (the setting is on Profile), and the Auth area (onboarding, login, sign up, forgot password, privacy policy, the auth navigator headers, `FormInput`, `FormButton` and the shared `CurrencyPickerModal`); the Transactions area (add and edit expense and income, the list, the detail and receipt screens, `AmountInput`, `DateInput`, `CategorySelector`, `ImagePickerModal`); the Profile area (Profile, Edit Profile, Contact Us; Profile and Sign up share `CurrencyPickerModal`); the Statistics screen (rewritten on Victory Native XL, see the Statistics note below); Savings and Savings History; and the whole Split area (the Split list and create group form, Create Split and `SelectModal`, group detail, split detail, all transactions, settle up, IOUs and New IOU, Friends and Balances, Split History, Invitations). The colour classes are the `ThemeColors` tokens in kebab-case (`surfaceMuted` is `surface-muted`, `onPrimary` is `on-primary`); they point at CSS variables that `ThemeProvider` sets from the palette (`src/theme/cssVars.ts`), so they follow the System, Light or Dark setting without `dark:` variants, and `__tests__/tailwindTokens.test.ts` fails if the token list in `tailwind.config.js` drifts from `ThemeColors`. - Tags: a transaction may carry `tags: string[]` (free text, at most 5, 24 characters each, distinct ignoring case; written only when present on add, always on edit so an empty array clears them; absent on every older document, no backfill). The rules live in `src/utils/tags.ts`: read tags through `sanitizeTags`, never trust the raw field. `users/{uid}/tags/{t_<lowercased tag, URL-encoded>}` (`name`, `createdAt`, `lastUsedAt`) is only the suggestion list (`src/services/TagService.ts`, `useKnownTags`), written after a save without blocking it; the transactions hold the real data, so a missing list loses nothing. The form field is `src/components/form/TagField.tsx`, read-only chips are `TagChips`. The Transactions screen filters through one pure function, `src/utils/transactionFilter.ts` (period, search text and tag all apply together; search also matches tags); add any new filter there, not in the screen. No rules or functions change was needed (owner-only subcollection; the triggers only derive money fields), and old app versions ignore the field and keep it when they edit (they use `txn.update` on named fields). Tags are not shown on Home, Statistics or split screens yet.
- Receipt photos: a transaction stores the URL in both `imageUrl` and the older `image` (Add Expense used to write only `image`, while the other screens read only `imageUrl`, so a receipt added there never showed). Always write through `receiptFields(url)` and read through `receiptUrlOf(tx)` (`src/utils/receipt.ts`); clearing a receipt must clear both fields.
- Rules stage A (`firebase/firestore.rules`, 52 tests in `firebase/tests/rules.test.mjs`; DEPLOYED to `trackaexpense` on 2026-11-10 with the owner's approval, then smoke-tested with the app: groups list, group and splits read, and a group edit that creates an invitation all work): group membership is recognised by email or by uid in `memberIds` (group, its splits and settlements, invitation checks); `memberIds` can only be written by the server (a client cannot create a group with it or change it); a group's `createdBy` cannot change on update; an invitation can only be created by a member of that group and must start as `pending`.
